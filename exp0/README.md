# Эксперимент 0: отпечаток исполнения φ, однообразие модели, потолок разнообразия

Запуск на сервере (4× RTX 6000 Ada, Linux) одной командой из корня репозитория:

```bash
bash exp0/run.sh                 # полный прогон: Часть А → генерация → Части Б, В → отчёт
SMOKE=1 bash exp0/run.sh         # быстрый сквозной прогон (6+6 задач, мало сэмплов), ~15–25 мин
bash exp0/run.sh partA report    # отдельные этапы: tools data partA gen analysis report
```

Результат: `exp0/results/report.md` (+ `figures/*.png`, `partA_auc.json`, `partB.json`, `partC.json`,
сырые генерации `generations/*.jsonl`). Все этапы возобновляемы: при повторном запуске
готовое берётся из `results/cache` и пропускается.

## Диск (лимит 20 ГБ)

Всё — venv, кэши HF/vLLM/Triton, модели, данные, результаты — лежит внутри `exp0/`.
Перед каждой загрузкой проверяется бюджет `DISK_LIMIT_GB` (по умолчанию 19).
Примерная пиковая занятость: venv ≈ 9 ГБ + одна модель ≈ 4.5 ГБ + JRE/JPlag 0.15 ГБ + данные/результаты < 1 ГБ.
Веса удаляются сразу после своей генерации (`KEEP_MODELS=1` — оставить). Xet chunk-cache HF отключён.
APPS читается потоком по HTTP, на диск попадают только отобранные задачи.
Если vLLM уже стоит в системном python3 — venv не создаётся.

## Что где

| файл | что делает |
|---|---|
| `src/harness.py` | песочница-ребёнок: rlimits (память, CPU, размер файлов), отключение опасных os/shutil/subprocess, таймауты на каждый запуск, большой стек для рекурсии; трассировщик `sys.settrace`+`sys.setprofile`: исполненные строки, вызовы, глубина стека и рекурсии, попадания по строкам (→ вложенность реально итерирующих циклов), вызовы heap/sort/set/dict/counter/deque/bisect/itertools/memo/math/re; плюс замеры времени без трассировки |
| `src/scaler.py` | «лестницы» растущих входов из тестов самой задачи (без LLM): рост списков/строк/чисел с сохранением сортированности и уникальности; для stdin — распознавание форматов «n + список», «n + n строк», «одно число», «одна строка»; плюс «естественная» лестница из тестовых входов |
| `src/fingerprint.py` | φ = L1 масштабирование (наклон log-log числа строк, а когда работа скрыта в C-builtins — времени; класс O(·); рост глубины рекурсии), L2 схема (рекурсия none/linear/branching, мемоизация, глубина реально исполняемых вложенных циклов), L3 примитивы (что реально исполнилось). `d_φ = 0.6·d1 + 0.25·d2 + 0.15·d3` — веса «большой / средний / малый» заданы заранее (`W_PHI`), не подбираются на парах; вариант с равными весами печатается только как проверка чувствительности |
| `src/curated.py` | наша разметка: 21 задача × 2–6 алгоритмов × 2–3 стилистически разных реализации = 135 программ, 402 пары (72 «один алгоритм»). Трудные положительные пары (bisect против ручного бинпоиска, DP сверху вниз против снизу вверх) специально помечены как «один алгоритм» |
| `src/pacd.py` | PACD (arXiv:2510.27063). Публичного URL я не нашёл — положите данные в `exp0/data/pacd/` (форматы описаны в файле), этап А подхватит их автоматически |
| `src/part_a.py` | AUC (бутстреп по семействам задач) для d_φ, отдельно по уровням, обученного d_φ (логрег, leave-one-family-out), JPlag 6.3, difflib, AST, эмбеддингов (Qwen3-Embedding-0.6B, UniXcoder) — на **одних и тех же** парах; точность/полнота группировок; повторяемость отпечатка (второй независимый замер); порог τ |
| `src/gen_worker.py`, `src/generate.py` | vLLM или HF transformers (`BACKEND=hf`: для GPU, которые текущий vLLM не поддерживает, например V100 — там же автоматически float16; сэмплы многих запросов генерируются батчами до `HF_BATCH`, остановка по `<|im_end|>`, `repetition_penalty=1.0` явно, флаг `truncated` у каждой строки), по процессу на GPU (data parallel), Qwen3.5 в режиме только текста, non-thinking. | `src/data.py` | MBPP+ (EvalPlus: полный тест-скрипт задачи, base + plus входы, сотни проверок вместо трёх; при недоступности — sanitized MBPP с предупреждением) и APPS-introductory; эталоны проверяются; в задаче хранится рецепт лестницы, а не сами входы |
| `src/analysis.py` | Б и В считаются отдельно для **нетривиальных** задач (основные таблицы) и для всех; тривиальная задача = все измеримые эталоны — O(1)-формула без рекурсии. Б: число групп среди правильных по L1/L2/L3/φ/τ-кластерам, сравнение с людьми (APPS, с прореживанием до одинакового числа решений), зависимость φ от seed (AMI + перестановочный тест). В: pass@k и E[#групп@k] при равном бюджете — точные комбинаторные оценки (без Монте-Карло), для смешанных пулов — стратифицированные; парный бутстреп прироста |

## Ручная разметка 200 пар — обязательный шаг

Без неё часть А не завершена (отчёт помечает это явно): наш курируемый набор написан тем же автором, что и
отпечаток, и состоит из учебных задач, где алгоритмы различаются в основном сложностью, — это оптимистичный
случай. Планка 0.73 из DivAlgo получена на C++ и чужих парах и печатается только для справки; настоящий ответ
части А — сравнение с JPlag и эмбеддингами на одних и тех же парах, в первую очередь на ручной разметке.

После этапа `analysis` создаётся `data/labels/manual_pairs_todo.jsonl` (+ `.md` для чтения): 200 случайных пар
правильных решений одной задачи, заметно различающихся по тексту. Проставьте `"same": 1/0`, сохраните как
`data/labels/manual_pairs.jsonl` и выполните `bash exp0/run.sh partA report` — пары войдут в таблицу AUC как набор `manual`.

## Проверка кода (ревью gpt-6-astra через Codex CLI)

Код прошёл независимое ревью; исправлено всё, с чем я согласен, в том числе:
`sys.exit()` внутри тестируемой функции больше не засчитывается как пройденный тест; сбой JPlag даёт
пропуск, а не расстояние 1.0; правильное решение без отпечатка не считается «группой»; кэши адресуются
по содержимому (тесты, лестница, хэш исходников трассировщика), `.done` генерации хранит хэш конфигурации;
пропущенные промпты пишутся как неверные сэмплы (честный бюджет), `k` не превышает размер пула; анализ
читает только завершённые генерации; лестница выбирается **один раз на задачу** по эталонным решениям;
числа, равные длине массива (`solve(n, a)`), растут вместе с ним; масштабирование требует ≥3 размеров,
обрезанные лимитом точки не подгоняются как точные; исправлен подсчёт вложенности циклов (цикл первой
строкой функции); примитивы — только по реальным событиям вызова (кроме литералов/конструкторов);
калиброванные повторы замеров времени; сторож `faulthandler` против C-кода, держащего GIL; запрет записи
файлов вне рабочей папки песочницы; число воркеров ограничено объёмом RAM; монитор диска во время работы;
uv/Python ставятся внутрь `exp0`; при сбое vLLM — быстрый отказ и (опционально, `HF_FALLBACK`) повтор на HF
в чистых процессах с записью бэкенда в каждую строку; prefix caching выключен (для гибридного Qwen3.5 он
экспериментальный); официальный формат входа UniXcoder; PACD сравнивается только внутри одинаковой семантики;
обученный d_φ — leave-one-*family*-out; курируемые программы с ошибкой исключаются; τ-кластеры строятся внутри
собственной популяции условия; отдельный тест зависимости *правильности* от префикса; формулировки
«группы отпечатка» вместо «алгоритмов» и «связь не обнаружена» вместо «seed игнорируется».

## Известные ограничения

* «Инструкции» = исполненные строки Python (line events). Работа внутри C-builtins (`min`, `set`, склейка
  списков, `x in list`) видна только через замеры времени без трассировки (`b_time`). Поэтому лестницы
  продолжаются только для замеров времени до 200 тыс. элементов / 1e7, а время берётся как минимум из калиброванных
  повторов (до 50, ≥ 20 мс суммарно); в подгонку идут точки выше пола накладных расходов.
  Остаточное слепое пятно: очень быстрые C-операции (`s.count(...)`, `x in t` с ранним выходом) на 200 тыс.
  элементов всё ещё ниже порога и получают O(1). На 200 эталонах MBPP+ в O(1) попадают 71: почти все —
  настоящие формулы, они уходят в «тривиальные» задачи.
* Шум времени: трассируемые программы закрепляются за отдельными физическими ядрами, параллельность
  отпечатков ограничена `FP_WORKERS` (по умолчанию половина ядер); повторяемость замеряется и печатается в отчёте.
  Локально (Windows, без закрепления, 6 параллельных задач) 10 из 135 программ сменили класс при повторном
  замере — все на границе O(n) / O(n log n), за счёт наклона по времени. Устойчивая оценка Тейла–Сена
  повторяемость не улучшила (это сдвиг всей кривой между прогонами, а не выбросы), поэтому оставлен МНК.
* Наклон по времени между прогонами гуляет на ±0.1–0.4, поэтому граница O(n) / O(n log n) для работы,
  скрытой в C (например, `sorted`), ненадёжна; в d_φ половина d1 — непрерывная разница наклонов, она к этому мягче,
  чем точный ключ.
* Граница между O(n) и O(n log n) по наклону хрупкая (на этих размерах разница ≈ 0.15).
* Масштабирование stdin в APPS эвристическое; если формат не распознан, используется естественная лестница
  тестовых входов (шумнее).
* Песочница — процесс с rlimits, отключёнными опасными функциями и запретом записи вне своей папки, но не
  контейнер (нет cgroups/namespace). Не запускайте под root; для полной изоляции запускайте в контейнере.
* В песочнице заблокирован `ctypes` (через него можно обойти защиту), поэтому `pandas` не импортируется;
  numpy работает.
* Флаг мемоизации — эвристика (рекурсия + lru_cache или реально использованный dict).
* Группы отпечатка ≠ алгоритмы. Точный ключ φ склеивает одно и то же реже, чем нужно (полнота ~0.4–0.5), а
  τ-кластеры, наоборот, склеивают разные алгоритмы (точность ~0.3). Абсолютные числа групп не читаются как
  «число алгоритмов»; осмысленны относительные сравнения: модель против людей, условие против обычного сэмплирования.
* PACD публичной ссылкой не найден; без него и без ручной разметки таблица A строится только на нашем наборе.
